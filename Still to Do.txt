## The order of work -- Ken's ruling, 2026-11-11

All the installers and the Store submission are redone in one pass, *after* the
open defects are fixed. The queue emptied on 2026-11-11 and the Windows half of
the pass was done on 2026-11-12 for 0.9.3. Four more defects were then fixed on
2026-11-23 -- one tab per file whatever the caller spells the path as, no prompt
about a change the editor made itself, the offer to close stale tabs when a
solution is opened, and the last block of a file that does not end in a newline
-- so the pass was redone for 0.9.4. What is left is below.

Built and signed for **0.9.4** on 2026-11-23, all four from one signed stage,
each checked by unpacking or by reading its signature rather than from a log:

  - dist\AlignThree-0.9.4-setup.exe         signed, uninstaller stub included
  - dist\AlignThree-0.9.4-windows-x64.zip   signed binaries inside
  - dist\AlignThree-0.9.4-x64-store.msix    unsigned, for Partner Center
  - dist\AlignThree-0.9.4-x64.msix          signed, identity and version read
                                            back from the unpacked manifest;
                                            **built but not released** -- see
                                            the ruling below

  Ken's ruling, 2026-11-24: **releases no longer carry an MSIX.** The Microsoft
  Store replaces the self-hosted package -- whoever wants the packaged app
  installs it from the Store, and the installer is what the site offers to
  anyone who wants SpecTableConverter.exe on a command line. The Store package
  is still built and uploaded at each release. The self-hosted one stays in
  dist\ and stays documented, because the script still makes it and it may be
  wanted again.

  The two MSIX packages hold the same 68 payload files; the signed one carries
  AppxSignature.p7x and AppxMetadata\CodeIntegrity.cat as well, which is the
  whole of the difference. Identity is unchanged from 0.9.3
  (KenPughInc.AlignThree), so the self-hosted package would upgrade 0.9.3 in
  place for anyone who installed that one.

  scripts\verify_install.ps1 -PerUser passes every check against 0.9.4, run on
  2026-11-23, so the three facts a store submission asks to be verified by hand
  -- silent install, the Add or Remove Programs entry, no bundleware -- are
  evidenced for this build: exit 0 in 7s with no restart, an HKCU entry reading
  AlignThree / Ken Pugh, Inc. / 0.9.4, 41 files and nothing bundled, all four
  executables signed and timestamped on one certificate (unins000.exe
  included), the converter running with Qt off PATH, and a clean removal.

  The 0.9.3 install on this machine was not disturbed. A per-user run registers
  in HKCU while that one is in HKLM, so the clash guard reported "already
  installed elsewhere, and left alone" and -Force was not needed.

The version bumped to 0.9.4 in CMakeLists.txt (f69ab8b) because a rebuild under
the old number would carry the same identity and the same 0.9.3.0 version with
different contents, which Windows has no reason to install over what is there.
package_windows.ps1 gained -Version for it (16129eb): the name used to come
from the newest *reachable* tag, so a tree bumped past its last tag could not
name its own artefacts.

**Sectigo's timestamp server refuses to timestamp.** Every Sectigo endpoint
fails with 0x80096005 (TRUST_E_TIME_STAMP) while DigiCert's and SSL.com's
work, and signing with no /tr at all succeeds -- so it is the TSA, not the
token. 0.9.3 and 0.9.4 are both timestamped by DigiCert, passed -TimestampUrl;
nothing in the scripts changed. If Sectigo's comes back and that matters, the
artefacts can be re-signed and repacked, since none of this is released.

## Open defects

The four defects this section listed on 2026-10-25 are all closed (see
"Finished"), as is the mnemonics work added to the queue on 2026-11-11 and the
built-in type colouring. What is left is one decision and one known wart.


[ ] The two rules beside the built-in one have the problem it just had: they
    match the whole line too, so "Then the answer is Yes" colours Yes, "Given
    In the beginning" colours In, "Then the entry is Valid" colours Valid and
    "Scenario A True Statement" colours True. Measured, 2026-11-11. Whether
    those words should also be confined to a table cell is a decision, not a
    defect -- Valid and Yes do read as cell values, and nobody has complained.

[ ] Swift's Package.swift excludes the copied .spectable files by name, so
    deleting a specification leaves a stale entry there. Known and deliberately
    left. SwiftPM reports it as
    "Invalid Exclude ...: File not found." and builds anyway -- measured, not
    assumed. Nothing else enumerates files by hand; C++'s CMakeLists globs
    test_*.cpp with CONFIGURE_DEPENDS, and the other seven languages have no
    such list.


## Finished since the last survey — recorded here so the list is not re-read

[x] A built-in type name is coloured only where a type can be written,
    2026-11-11. The rule matched the whole line, so "Scenario Define with a
    String", "Calculation Empty String Returns Zero" and "Calculation Heading
    Text Is Parsed" all had a word in them lit up as a type, and so did a
    Define value and the prose of a named comment. Colour now goes to a table
    row and to the type reference at the end of a line, where the modifiers may
    follow it; a line is read for its shape before any word in it is coloured,
    which a rule cannot do. Everything that overrode the colour before still
    does, so ": String" stays grey as the attribute-set reference and a word
    inside a # comment stays green. Measured per character off the layout, 19
    cases.

[x] A removed specification takes its generated code with it, 2026-11-11.
    Deleting a .spectable in the Solution Explorer now deletes the test and the
    glue for it in whatever language the project generates, and a project or
    solution build sweeps anything else left over. Production code is never
    touched -- Ken's ruling. The rule that decides what a deleted
    specification owns is src/model/GeneratedFileNames.h: it normalises a file
    name to lowercase alphanumerics and matches the nine test and glue
    spellings, so one rule covers all of them instead of four naming functions
    per language, and copies or backups are never in range. The two shared
    files that carried a deleted specification's entries are pruned too:
    Rust's crate root and subdirectory mod.rs now go through
    SourceScan::dropEntriesForMissingFiles like production/mod.rs already did,
    and Java's TableHelper/ProductionHelper drop a merged method whose
    generated String or Typed class is no longer written.

    Verified by compiling and running both ends, not by reading the output.
    Java with AddressCorrection deleted: mvn clean test, 35 tests, 0 failures
    (39 less its four). Rust with Bowling deleted: cargo test, 30 passed
    (39 less its nine), and lib.rs no longer declares the two modules whose
    files are gone while the other sixteen stay. One honest footnote: the Java
    pruning rule first read "String" in toListString as a generated class,
    looked for a common/String.java that cannot exist, and dropped three
    methods API_Test.java calls six times. The compiler caught it; the rule now
    requires a name in front of the suffix.

[x] The live geocoder reports a timeout and says to run it again. Ken's
    ruling, 2026-11-11: no record-and-replay. A call that cannot be made at
    all now raises a timeout naming the URL and ending "the service did not
    answer, so run the test again", in all nine transports. The point is that
    a broken test and a failed assertion must not look alike in the output:
    the service is live, so an unanswered call says nothing about the
    specification.

[x] Every menu has mnemonics, 2026-11-11. The File menu went first (15a578c,
    so Alt-F-S saves); Edit, View, Build, Analyze, Git and Help followed --
    40 labels, each letter unique within its menu, the menubar titles F E V G
    B A H already distinct. The About label also titles the About box, so only
    the menu item carries the ampersand.

[x] The docstring marker already coloured all three quotes. The entry was
    stale: commit 34e8b85 (2026-09-09) fixed it, and a per-character dump of
    the highlighter's output confirms all three quote marks are coloured in
    every valid shape, in .spectable and .featurex alike. A probe that read
    "NOT ALL THREE" turned out to be my own invalid syntax -- the parser wants
    the three quotes alone on their line -- and not a defect.

[x] The AddressCorrection half of "bug to fix.txt" is satisfied in all nine
    languages, checked 2026-11-11: no placeholder "string"/"number" cells, no
    hand-built JSON, and whole-object comparison throughout. One deviation is
    deliberate and documented: matched addresses compare their String forms in
    both scenarios, because the two share a step phrase and only the String
    form honours ?DNC?.

[x] ExampleTests regenerated in all nine languages and verified by running all
    nine, 2026-10-25 (SpecStudioExampleTests 05e9f07). The staleness this list
    described is gone: Record Filter Example no longer asserts the example row
    its specification dropped, its Description spelling is fixed, and the six
    C++ cell wrappers carry the comparison operators and empty() from the
    external findings report. Each suite ran on its own -- 39 tests, no
    failures, in Java, Python, Go, Rust, C#, JavaScript, TypeScript, Swift and
    C++. Serially on purpose: two toolchains at once is what ran the box out of
    memory the first time this was attempted.

[x] Leading whitespace is ignored. Ken's ruling, 2026-10-25: people may wish
    to indent for their own purposes. The parser used to discard any indented
    line that was not a pipe row -- it served named-comment continuation, and
    served it by dropping the text -- which also swallowed an indented step:
    a scenario with an indented When and Then analyzed clean and generated a
    test holding only the Given. The skip is gone, so every line is read for
    what it says at any column. Four specifications were relying on the
    discard for wrapped prose (Common Types, Types and Formatted Dollar in
    VariousTests, Types in ExampleTests) and now carry the leading backslash
    the syntax document has always asked for, which also means their text
    reaches the comment it was written under for the first time. Documented in
    syntax section 2 and 4.1.1 and in the User Guide; the four corpora are
    back at 67 / 2 / 8 / 0.

[x] The stale Java .spectable copies are deleted. Nineteen of them under
    Java/SpecTableVariousTests/src/test/java/spectable/, every one with an
    authoritative original in TestProject/ and nothing reading them at
    runtime. mvn clean test afterwards: 58 tests, 0 failures.

[x] Rust falls back to a default variant. genRustProductionEnum now derives
    Default with #[default] on the first variant and emits From<&str>,
    From<String> and Display, with the unrecognised value falling back to
    default() because a From cannot fail. Generated, cargo built, and run
    (3/3). Honest footnote: the premise in "More to do.txt" does not hold
    today -- a DataType field crosses into Rust as <Name>Typed text, so no
    generated Rust calls EnumName::from, and the old bare enum compiled fine.
    The fallback is there for production code that does call it, and the
    generated comment points at a fallible parse for the case where the
    unrecognised value matters.

[x] WhenThen is documented. It works just like a When or a Then, and is for
    one table whose columns are part When data and part Then data: the
    scenario has its Given, and the table goes under the WhenThen. In the
    syntax document at 2.7, in the grammar, and at 4.6; in the User Guide
    beside the step keywords. What it generates was read off a run in all
    nine languages -- an ordinary step call handed the whole table, keyword in
    the method name. Two consequences are stated too: an And under a WhenThen
    continues as a WhenThen, and a WhenThen in a Cleanup block is an error.

[x] The external findings report is closed. Every item is fixed, documented,
    or ruled on; the last of them was the most-vexing-parse note, now in the
    User Guide under "Checking that a value is refused".
